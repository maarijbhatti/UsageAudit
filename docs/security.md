# Security model

Authentication is owned by NestJS. Argon2id uses 64 MiB, three iterations and one lane. Random 256-bit access and refresh values are stored only as SHA-256 hashes. Access lasts 15 minutes, refresh lasts seven days, refresh rotation locks the old session row, and replay revokes the entire token family. Logout revokes the family. All protected APIs recheck database session state.

Cookies are HttpOnly (except the separate CSRF token), SameSite=Lax, and Secure when `NODE_ENV=production`. Mutations require exact configured origin plus a session-bound CSRF header. Registration/login require the origin check too. Redis-backed rate limiting protects authentication; Redis failure closes authentication requests rather than silently bypassing limits. The local Next proxy is the single origin. In production place it behind HTTPS, keep the API private, and explicitly configure trusted proxy/network behavior; do not trust arbitrary forwarded-IP headers.

One Nest guard enforces permissions and membership. VIEWER reads/downloads; ANALYST imports, maps customers, runs audits and reviews; ADMIN additionally configures metrics, prices, Stripe and members; OWNER additionally closes the organization. Admins cannot assign/remove peer administrators, owners cannot be removed through member endpoints. Organization closure is a soft closure preserving immutable evidence, with connection secret revocation and schedule disabling.

Every resource lookup is organization-scoped. Composite foreign keys reject cross-tenant nested references. Worker jobs load their organization and resource from the durable outbox, not client-supplied queue payloads. Scheduled jobs recheck the creating member's privileges. S3 objects use organization-prefixed unguessable paths; there are no public buckets, unsigned browser object URLs, or credential values in API responses.

Provider secrets use AES-256-GCM with random IV and organization ID as authenticated associated data. The 32-byte key is external to PostgreSQL. In production replace the local key provider with a KMS/managed secret service and establish key versioning/re-encryption. Stripe keys must have a restricted `rk_test_` or `rk_live_` prefix and read permissions only. Stripe does not expose an API that reliably attests all permissions of a key: the integration verifies required reads, and all adapter calls are GETs; the operator must configure the restricted key without writes. No SDK write methods are called.

Raw CSV is stored privately, size-limited, streamed, and schema-validated. PostgreSQL statements are parameterized. Formula-leading CSV values are prefixed with an apostrophe on export. Reports are downloaded only after session and membership checks. Errors avoid returning stack traces or secrets; logs use structured JSON without source financial records. Audit actions/reviews are append-only.

Production hardening still required: independent security review, least-privilege service credentials, backup/restore drills, managed encryption keys, retention/deletion policy, TLS, log access controls, process supervision, queue monitoring, patch management, and alerting. Password reset, email verification, MFA and SSO are outside this implemented MVP. Data is scoped in application SQL and composite constraints; PostgreSQL row-level security is not enabled. A database administrator remains a privileged actor.

Dependency audit initially identified two moderate TypeORM transitive advisories. `typeorm>glob=14.0.2` and `glob>minimatch=11.0.1` are pinned to patched releases with compatible runtime/export APIs. The updated production audit reported zero advisories when executed; that is a point-in-time result, not a guarantee against future disclosures.
